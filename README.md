# WordPress REST API Automation Tests

Проект автоматизированного тестирования **WordPress REST API** (посты и комментарии) с использованием **Java, Rest Assured, TestNG, Allure** и прямого доступа к базе данных для валидации.

---

## Описание

Набор тестов проверяет ключевые сценарии работы с постами и комментариями в WordPress через REST API:

- **Создание, редактирование, удаление постов** (с проверкой статусов, валидацией параметров, авторизацией)
- **Создание, редактирование, удаление комментариев** (привязка к посту, проверка ошибок)
- **Получение постов и комментариев** (одиночных и списков, с учётом прав доступа)
- **Валидация через базу данных** – после каждого API-запроса проверяется фактическое состояние в таблицах `wp_posts` и `wp_comments`.

Все тесты используют **базовую HTTP-аутентификацию**, работают с БД MySQL и имеют полную очистку созданных сущностей после каждого метода.

## Настройка

### 1. Клонирование репозитория

```bash
git clone https://github.com/MielPops828/Wordpress-API-Project
cd Wordpress-API-Project
```

### 2. Подготовка базы данных

Проект подключается к локальной MySQL с параметрами:

- URL: `jdbc:mysql://localhost:3306/wordpress`
- Пользователь: `wordpress`
- Пароль: `wordpress`

Убедитесь, что у вас запущен MySQL и создана база `wordpress` со стандартной структурой таблиц WordPress.  
Если вы используете другие учётные данные, измените их в классе `DatabaseConnection.java`.

### 3. Настройка конфигурации

Отредактируйте файл `src/test/resources/config.properties`:

```properties
base.url=http://localhost:8000
path=/index.php
basic.username=YOUR_USERNAME
basic.password=YOUR_PASSWORD

update.title=Update Post
update.content=Some update content
update.valid.status=publish
update.invalid.status=123
update.postId=12
update.non.exists.id=1000

comment.non.exists.id=1020
comment.invalid.id=abc

delete.non.exists.id=2040
delete.invalid.id=abc

post.data.count=3
per.page=50

post.non.exists.id=1020
post.invalid.id=abc123
```

- **base.url** – адрес вашего WordPress (обычно `http://localhost:8000` для локального окружения).
- **path** – путь к index.php (для корректной маршрутизации REST).
- **basic.username / basic.password** – учётные данные пользователя с правами на создание/удаление постов и комментариев.
- Остальные параметры – тестовые данные (ID для негативных сценариев, количество создаваемых записей и т.д.).

### 4. Установка зависимостей

```bash
mvn clean install
```

## Запуск тестов

Все тесты запускаются через `testng.xml`, который содержит все классы и настроен на последовательное выполнение (без параллелизации).

```bash
mvn test
```

или для генерации Allure-отчёта:

```bash
mvn test allure:report
```

### Отдельные тесты

Можно запустить конкретный класс:

```bash
mvn test -Dtest=CreatePostTest
```

или конкретный метод:

```bash
mvn test -Dtest=CreatePostTest#testSuccessCreatePost
```

## Генерация Allure-отчёта

После выполнения тестов результаты сохраняются в `allure-results`.

Открыть отчёт в браузере:

```bash
allure serve allure-results
```

или через Maven:

```bash
mvn allure:serve
```

Отчёт содержит:

- Статистику по тестам (успешно/упало/сломано)
- Время выполнения
- Логи и вложения
- Аннотации `@Epic`, `@Feature`, `@Severity`, `@Description` для удобной навигации

## Структура тестов

### Базовый класс `BaseTest`

- Инициализирует `RequestSpecification` с базовым URL и путём (`/index.php`).
- Загружает конфигурацию через Owner (`Configuration`).
- После каждого теста (`@AfterMethod`) удаляет из БД все посты и комментарии, созданные во время теста (списки `createdPostIds` и `createdCommentIds`).

### Работа с базой данных

- `PostQueries` / `CommentQueries` – выполняют прямые SQL-запросы для создания, удаления, проверки существования и получения сущностей.
- Это позволяет не полагаться только на API для верификации – мы проверяем, что данные действительно записались в БД или удалились.

### DTO и Request-объекты

- `PostRequest`, `CommentRequest` – сериализуются в JSON для отправки в теле запроса.
- `PostEntity`, `CommentEntity` – используются для сравнения данных из БД с ответами API.

### Шаги (`PostSteps`, `CommentSteps`)

- Инкапсулируют часто используемые API-вызовы (создание поста / комментария) с генерацией уникальных данных (UUID).
- Возвращают ID созданной сущности для дальнейшего использования.

### Тесты

Каждый тест проверяет:

- HTTP-статус код,
- Структуру и содержимое JSON-ответа,
- Состояние в БД (с помощью Queries),
- Коды и сообщения ошибок для негативных сценариев.

---

## Примечания

- **Авторизация** – используется базовая HTTP-аутентификация (`auth().preemptive().basic()`).
- **Очистка БД** – важна для воспроизводимости; все созданные тестами посты и комментарии удаляются после каждого метода.
- **Негативные сценарии** – используют предопределённые ID из `config.properties` (например, `comment.non.exists.id=1020`). Убедитесь, что эти ID действительно не существуют в вашей БД.
- **Параллельный запуск** – не рекомендуется, т.к. тесты используют общую БД; при параллельном выполнении возможны конфликты.
- **База данных** – перед запуском убедитесь, что MySQL доступен и структура таблиц соответствует стандартной WordPress.
